# 爱心社社员档案系统 · 飞书多维表格结构分析

> 解析时间：2026.10.11　解析对象：北大爱心社两个学年的多维表格（Base）  
> 数据来源：飞书 Base 实时读取（base-block / field / view / form / dashboard / workflow）

---

## 一、总体结论

两个 Base 是**同一套系统的两个学年版本**，采用完全一致的架构：

```
社员档案（主表，一人一行）
   │  ← link 关联列（127 列 / 12 列）
   ▼
各部组活动问卷表（一张活动 = 一张表，"反馈 + 学时"问卷）
   │
   ▼
仪表盘（招新画像 / 单活动结果分析）
```

- **主表负责"人"**：姓名、学号、院系、年级、性别、入社时间、感兴趣的部组等身份与画像信息。
- **子表负责"事"**：每场活动独立成表，收集参与反馈、志愿学时、评分、感想等。
- **中间靠 link 字段打通**：子表有一个指向「社员档案」的关联列，主表侧生成对应关联列，从而形成"某人参加过哪些活动"的矩阵，可反查、可统计学时。

三个库都开启了**高级权限**（`is_advanced = true`），适合各部组多人分头维护自己的问卷表。

### 4. 自动化流程（Workflow，唯一 1 条，已启用）

标题：**当编号新增 + 档案没有该姓名和学号 = 档案新增该姓名和学号**

```
触发：志愿者编号信息统计表　新增/修改记录，且"您的学号"非空
  ↓
查找：社员档案中 学号 与 姓名 同时匹配的记录
  ↓
条件判断：匹配条数 == 0 ？
  ├─ 是 → 在社员档案新增记录（姓名、学号、入社日期 = 当前时间）
  └─ 否 → 结束
```

**作用**：把"志愿者编号登记"变成社员档案的自动补充通道，自动去重，避免人工重复录入。

## 四、共同特点与设计机制

1. **主从关联矩阵**：主表 1 行 = 1 人；子表 1 行 = 1 次参与；靠 link 双向往返。既可"看人查活动"，也可"看活动查人"。
2. **问卷即数据源，模板化生成**：每场活动一张表，字段高度统一（参与时间、志愿时长、评分、感想、能否宣传、问题与建议 + 活动专属题 + 社员档案关联列）。用「模板」表复制生成，保证各活动口径一致、可横向汇总。
3. **双维组织**：部组（9 个）× 学期（25暑/25秋/26春/26秋），目录即报表维度。
4. **人群画像**：院系 / 年级 / 性别 / 入社时间 / 感兴趣部组 → 驱动招新与建设决策。
5. **开放题可视化**：大量使用词云处理"感想/建议/想说的话"等自由文本。
6. **自动化补录**：25-26 用 Workflow 把编号登记表自动灌入档案，去重防重。
7. **数据质检视图**："检查多填/重名/升学" 这类专用视图用于查错，是运维层面的实用设计。
8. **权限分级**：两库均启用高级权限，支持多人（各部组）协作维护。

## 五、两库差异（版本演进）

| 维度           | 25-26               | 26-27             |
| ------------ | ------------------- | ----------------- |
| Block 数      | 161                 | 59（精简）            |
| 主表人数         | 2488（含历史全量）         | 1134（新学年为主）       |
| 主表字段         | 141（14 基础 + 127 关联） | 22（10 基础 + 12 关联） |
| 骨干字段         | 有（标记核心成员）           | 无                 |
| 自关联「父记录」     | 无                   | 有（支持层级归属）         |
| 编号登记表        | 有（1398 条）+ 自动同步     | 无                 |
| 自动化 Workflow | 1 条（编号→档案同步）        | 无                 |
| 意见反馈渠道表      | 无                   | 有（匿名建议箱）          |
| 日常工作学时表      | 无（并入活动表）            | 有（单独拆出）           |
| 仪表盘          | 2 个（含单活动分析）         | 1 个（招新画像）         |

**演进方向**：26-27 明显做了**瘦身与规范化**——字段收敛、目录简化、新增"日常工作 vs 活动"的学时区分、新增独立意见反馈入口；但把"编号登记自动同步"和"数据质检视图"这两个运维能力**丢掉了**，这是版本退步点。

## 六、对本项目（查询系统）的启示

1. **数据模型可直接复用**：查询系统若要还原"社员—活动参与"关系，核心是解析 127（或 12）个 link 字段 → 子表，把"参与矩阵"展开即可算出每人参与活动数、学时合计。
2. **主键选择**：应以 `姓名 + 学号` 联合去重（现有自动化即按此判断），`自动编号` 仅为展示序号，不可作唯一键（两库编号体系独立，26-27 从 2763 起延续 25-26 编号——说明编号在跨库延续，需注意跨库去重）。
3. **敏感字段警示**：身份证号、志愿者编号、微信号存在表中；若对外查询需强制脱敏与权限控制。
4. **需补的运维能力**：26-27 缺"重名/重复填写检查"视图与编号同步自动化，建议在查询系统侧补去重与一致性校验。
