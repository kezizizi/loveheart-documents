# 爱心社「爱心足迹」查询系统

北京大学学生爱心社的社员活动记录查询系统。输入姓名与学号，就能看到自己在爱心社的完整足迹：
参加过哪些活动、各拿多少志愿学时、在哪些部组留下过脚印，并能导出一张可以分享的海报。

<p align="center">
  <img src="docs/poster-sample.png" alt="爱心足迹海报示例" width="380">
</p>

> 海报示例由内置假数据生成（`AX_DEMO=1`），不含任何真实社员信息。

**当前规模**：自动发现 171 张活动问卷表（25-26 学年 125 张 / 26-27 学年 46 张），
注册表构建约 13 秒，单次查询约 5 秒。测试 162 项全绿。

---

## 它能做什么

- **一个入口查两个学年库**：同时查询 25-26 与 26-27 两个飞书多维表格，
  同一个人在两库的档案自动合并。
- **零硬编码的活动发现**：遍历多维表格的 Block 树，凡「有字段指回社员档案主表」的表
  即认定为活动问卷表；表所在的**文件夹层级**直接给出所属部组。
  骨干新增活动表后**不需要改任何代码**。
- **部组来自真实归档位置**：护老部、无障碍部、儿童部……取自表格在 Base 里的文件夹归属，
  不是入社问卷里填的「感兴趣的部组」。只认 9 个已知部组，
  文件夹名认不出的（如专项工作流「1+n第二期」）统一归入「其他」，不占部组标签位。
- **时间轴 + 学时明细**：按参与时间排序，逐个活动列出学时、评分与感想。
- **参与浓度聚合**：足迹部组数、活动场次、学期分布，以及「与 N 位伙伴同行」（按需计算）。
- **导出与分享**：活动记录 CSV；一键生成分享海报 —— 宽固定 1080，
  **高度随活动条数生长**，每一条活动都收录、不截断。
- **查不到时说明原因**：不是笼统的「没找到」，而是分清「姓名查不到」／「学号对不上」／
  「姓名查到了但档案里没填学号」，都给出同一个自助出口 —— 补录问卷。
- **入社日期口径透明**：优先采信档案里填写的真实日期；没有日期字段时用首次入档时间估算，
  页面上明确标出是「真实填写」还是「约为首次入档时间」。

## 快速开始

### 1. 装依赖

```bash
pip install -r requirements.txt
```

### 2. 建 `.streamlit/secrets.toml`

> ⚠️ 这个文件**不在仓库里**（已被 `.gitignore` 排除，CI 还有一道扫描确认它没被误提交）。
> 新克隆的仓库需要自己建一份。

```toml
[feishu]
app_id = "cli_你的应用ID"
app_secret = "你的应用密钥"

[base_25_26]
base_token = "第一个多维表格的 base_token"
main_table_id = "第一个多维表格里「社员档案」表的 table_id"

[base_26_27]
base_token = "第二个多维表格的 base_token"
main_table_id = "第二个多维表格里「社员档案」表的 table_id"
```

**凭证与坐标怎么拿**：

- `app_id` / `app_secret`：<https://open.feishu.cn/app> → 选你的应用 →
  「凭证与基础信息」。已部署过的话，也可以直接从 Streamlit Cloud 的
  **Settings → Secrets** 里抄。
- `base_token` / `main_table_id`：打开那个多维表格，看地址栏 ——
  `https://<租户>.feishu.cn/base/<base_token>?table=<table_id>&view=...`，
  两段正好对应。`main_table_id` 要取**社员档案主表**的那一个，不是某张活动表。

### 3. 配飞书应用（**这一步最容易漏**）

自建应用要能读到多维表格，必须同时满足两件事。

#### ① 开通接口权限，然后**创建版本并发布**

不发布不生效。

| 权限 | 是否必需 | 用途 |
|---|---|---|
| `bitable:app` | **必需** | 读写多维表格的字段与记录 |
| `base:block:read` | **强烈建议** | 读取文件夹层级 —— 这是判断「活动属于哪个部组」的**唯一**来源 |

> 只开通 `bitable:app` 也能跑，但拿不到文件夹结构，部组标签会统一退化成「其他」，
> 页面顶部会给出提示。想看到真实部组分布，就把 `base:block:read` 一起加上。

#### ② 把应用添加为**每一个**多维表格的协作者

⚠️ **入口不在「分享」面板里。** 分享面板的搜索框只搜成员和用户组，**根本搜不到应用**
（这一点很多人在这里卡住）：

> 打开多维表格 → 右上角 **「···」** → **「···更多」** → **「添加文档应用」**
> → 搜索应用名 → 权限选 **「可管理」**。

- **两个库都要做**：`爱心社社员档案（25-26）` 与 `爱心社社员档案（26-27）`。
  漏掉任何一个，那个库的数据就完全查不到，页面会出现「部分数据缺失」的提示。
- ⚠️ 这两个库都开了**高级权限**，所以权限必须给**「可管理」**；
  给「可编辑」仍然报 `1254302`，读不到数据。
- 如果「添加文档应用」里也搜不到你的应用，检查两处：
  ① 应用**发布版本**的「可用范围」需包含该多维表格的所有者；
  ② 应用至少开通了**任意一个云文档 API 权限**。

**常见报错对照**

| 报错 | 含义 | 怎么办 |
|---|---|---|
| `The role has no permissions`（1254302） | 该库还没把应用加为协作者 | 按上面的入口加，权限选「可管理」 |
| `One of the following scopes is required: [base:block:read]` | 权限没开通，或开通了没发布版本 | 补权限 + 创建版本并发布 |
| `field validation failed`（99992402） | 请求里带了超过 50 字的字段名 | 见下文「飞书接口的脾气」，已自动规避 |

## 它是怎么工作的

### 活动是怎么被发现的

```
遍历 Block 树（含文件夹）
  → 逐张表读字段，找出「有 link 字段指回社员档案主表」的表
    → 那就是活动问卷表
  → 表的文件夹层级 → 所属部组
```

全流程没有任何硬编码的 table_id 或活动名映射。主表里指向活动表的 link 字段，
则用来建立「活动清单的快速通道」。

### 两条查询通道，自动择一

> ⚠️ **先澄清一个容易误会的点：两条通道的遍历范围完全一样。**
> 都是「**该人有主表记录的库**」里的活动表 —— 「扫表」说的是**问法**，
> 不是「把范围放宽到全部库」。范围由下面的红线锁定，与走哪条通道无关。

| 通道 | 何时用 | 怎么问 | 请求量 | 可信度 |
|---|---|---|---|---|
| **关联通道**（快） | 主表的关联列里有数据 | 按主表里存的 record_id 精确取 | 只对**有该人记录**的表发请求，其余 0 请求 | 最高，完全规避重名 |
| **扫表通道**（兜底） | 该人的关联列**一个都没填** | 按姓名关键词问一次，再按 `关联 record_id > 学号 > 姓名` 判定 | 每张表 1 次；块信息里记录数为 0 的表直接跳过 | 只凭姓名命中的会标「待确认」 |

两者都是**每张表 1 次请求** —— 走扫表通道并不会因为「扫」而多花配额。
真正决定开销的是**表的数量**，而表的数量由「该人有档案的库」决定。

> 这个降级不是过度设计：真实数据里确实存在关联列全空的档案，
> 只走关联通道会把他们的参与记录**全部漏掉**。

**实测两种情形的开销**（当前共 171 张活动表：25-26 学年 125 张 + 26-27 学年 46 张）：

| 社员情形 | 遍历范围 | 实际请求 |
|---|---|---|
| 只在 26-27 有档案 | **46 张**（25-26 那 125 张一张都不碰） | 13 次，全部走扫表 |
| 两库都有档案 | 171 张 | 14 次（12 次走关联 + 2 次走扫表） |

> 两库都有档案时范围恰好等于全量，那是因为他本来就在两个库里都有记录，
> 不是因为「在扫全部库」。看第一行就知道红线是生效的。

**成员匹配（在主表里认人）要求姓名与学号同时命中**，只看姓名一律不算。
而判定**某条活动记录**是否属于本人时，允许「仅姓名」作为最弱证据命中（标为低置信）——
活动表里确实有连学号列都没有的表。

### 🚩 红线：遍历范围不可扩大

范围**恒等于**「该人有主表记录的那些库」里的活动表 —— 与「走哪条通道」无关，
也不会因为「这人参与记录多」就多扫几张。**永远不扩大到全部库。**

为什么：活动表访问是整条链路里最贵的一步，而飞书 API 调用量**有月度上限**。
对只在 26-27 有档案的社员（本届新生多数如此）擅自加扫 25-26，
就是**每次查询白打 125 张表**。想「多扫一点更全」的冲动必须压住 —— 那是把配额烧光。

守卫测试：`tests/test_member_query.py::test_collect_participations_never_widens_scope`

## 数据口径

| 项目 | 口径 |
|---|---|
| 主键 | 归一化后的「姓名 + 学号」。学号在 25-26 库是数字字段、26-27 库是文本字段，代码统一归一成纯数字字符串 |
| 活动名 | 表格名去掉「反馈、学时问卷」等后缀 |
| 部组 | 表格在 Base 里的文件夹归属。只认 9 个已知部组（护老部／无障碍部／儿童部／手语分社／资助部／组织部／宣传部／项目组／外联部）；认不出的一律归「其他」 |
| 学期 | 由文件夹名或表名里的「2025秋 / 26春」推导，统一成四位年份 |
| 入社日期 | 两库全部记录取最早。优先「入社日期」字段的真实值（25-26 库有该字段）→ 标「真实填写」；该字段缺失时（26-27 库只有「入社时间」学期下拉，没有日期字段），回退到 **Base 记录自身的创建时间**（自动字段，≈ 首次填写招新问卷的时间）→ 标「约为首次入档时间」 |
| 志愿学时 | 学时字段名不统一（「志愿时长」／「志愿学时」／「工时」），按正则探测；同一条记录有多个学时字段时求和 |
| 时间轴排序 | 参与时间 → 学期标签 → 记录创建时间，三级回退 |
| 海报画幅 | 宽固定 1080，高按内容算：`max(1620, 版头 + 统计卡 + 条数×行高 + 页脚)` |
| 缓存 | 活动注册表 24 小时（**全局共用**）；单次查询结果 10 分钟 |

## 飞书接口的脾气

下面每一条都对应一次真实事故。代码里已经处理掉了，但记在这里免得后人重踩。

| 现象 | 根因 | 现在的处理 |
|---|---|---|
| **部分活动表凭空消失**，且每次消失的还不一样 | 旧版接口把**限流**报成 `HTTP 400` + `code 99991400`（不是 429）。只按状态码判断会把请求直接判死，被限流的那张表就被丢掉，而注册表要缓存 24 小时。修复前连跑三次得到 169 / 165 / 171 张表 | 把 `99991400 / 99991404 / 1254290` 纳入可重试判定，退避重试 |
| **整张表的数据一条都拿不到** | 请求投影里带**超过 50 字**的字段名，飞书会拒掉**整个请求**（`field validation failed`，99992402），而不是忽略那一个字段。触发源是有人把问卷题干当成了列名（最长 78 字） | 在 API 边界统一剔除超长字段名；投影若被剔空则宁可报错，也不退化成「不带 field_names」（那会拉回全部字段、越过隐私边界） |
| 骨干改个列名，那张表就整体报错 | 缓存 24 小时的旧字段名触发 `FieldNameNotFound`（1254045） | 抛语义化的 `SchemaChangedError`，穿透单表隔离，丢弃注册表缓存重新探测后**只重试一次**。特意**不做**「丢掉未知字段继续查」——学时字段被改名时那样做会让整表学时**静默变成 0** |
| 关联通道取不到任何数据 | link 单元格的键名是 `link_record_ids`，不是旧文档里的 `record_ids` | 两种键名都兼容 |
| 按姓名筛选失效，返回整表 | 旧版 `records/search` **不认 `keyword`**（传了也返回整表） | 翻译成 `filter` 条件下推到服务端 |
| 整页报 `st.html body cannot be empty` | 一个部组标签都没有时组件返回空串，而 `st.html("")` 会抛异常 | 所有 `st.html` 收口到 `ui/pages.py::_html`，空内容直接跳过 |

**数据流**：`主表关联列 → 活动表 record_id → 参与记录 → 学时 → 汇总`。

## 隐私

- 只查询用户本人输入的那一条记录，**不展示任何其他社员的信息**。
- 身份证号、志愿者编号、微信号等敏感字段，在代码层就被排除在请求的字段投影之外 ——
  既不会被读取，也不会进入内存、页面或导出文件。
  唯一黑名单来源是 `config.SENSITIVE_FIELDS`，`feishu/client.py` 里有两道断言，
  并有单元测试守着。
- 「与 N 位伙伴同行」只会统计**人数**，不展示任何姓名。
- 飞书应用密钥只从 `.streamlit/secrets.toml` 读取，该文件已被 `.gitignore` 排除。
- 海报上**只出现姓名**，不含院系、年级、学号。

## 测试与自检

```bash
pip install -r requirements.txt -r requirements-dev.txt
python -m pytest
```

162 项测试，全部使用内存版客户端（`feishu/fake.py`）与录制的 JSON fixture，
**不触网、不需要密钥**。覆盖的关键行为：

- token 复用与续期、限流退避重试、403 不回退重试、新旧接口自动回退
- 超长字段名不进请求投影；投影不会被剔空
- 学号「数字字段 ↔ 文本字段」归一、姓名空白归一
- 活动表动态发现、部组来自文件夹而非问卷、排除主表自关联字段
- 学时字段命名差异都能识别
- 同名不同人的严防误判（link record_id 优先）
- 单表失败隔离、单库不可读时降级、表结构变更自愈
- 敏感字段永不进入请求投影或结果（隐私回归）
- 查不到时的三种归因
- 零活动记录不崩页、`st.html` 空内容被跳过
- 遍历范围不许扩大（红线守卫）
- 注册表缓存键里不许有会话级参数（API 配额守卫）
- 入社日期口径、时间轴三级排序、汇总聚合
- 海报画幅随活动数线性增长、HTML 转义、widget key 唯一性

**改了数据层代码之后**，用真实密钥跑一遍联调自检，确认整条链路还通：

```bash
python scripts/verify_live.py              # 全量自检
python scripts/verify_live.py --skip-query # 只建注册表，不查具体社员
```

它会打印：接口版本（新版 base/v3 还是回退旧版）、是否降级、两个库各自发现多少张活动表、
部组分布、字段探测抽样、敏感字段泄漏检查，以及一次真实社员查询的结果。
打印姓名时做脱敏处理，不会把社员个人信息写进日志。

## 常见问题

**页面提示「没找到你的档案」**
系统只做精确匹配（忽略空格），且**姓名与学号必须同时命中**。页面上会说明是哪一项没对上：
姓名查不到 / 学号对不上 / 姓名查到了但档案里没填学号。确实入社过的话，
走页面上的补录问卷链接即可。
> 备注：25-26 主表里有一批历史记录**没有填学号**，这批发真学号来查都会落到「档案里没填学号」
> 这一种归因。系统**不做**姓名兜底匹配 —— 那会拿同名误判换覆盖率，不划算。

**页面顶部出现「有 N 处数据没能取到」**
某张活动表读不到。其余数据仍然正常，提示里会列出是哪几张表。
先点一次页面上的**刷新数据**；仍然失败就按第 3 步检查权限与协作者。

**查不到 26-27 学年的活动**
该应用还没被添加为 26-27 库的协作者。见第 3 步 ②。

**骨干刚建了新的活动表，怎么让它出现？**
点一次页面上的**刷新数据**（注册表缓存 TTL 是 24 小时）。
注意：注册表缓存是**全局**的，所以这个动作对所有人生效。

**海报里中文变成方框**
中文字体没随之部署。确认 `assets/fonts/NotoSansSC-VF.ttf` 已提交进仓库。

**Windows 上改了代码没生效？**
Windows 没有 watchdog，Streamlit 不会监听被导入模块的改动。**手动重启服务**。
另外要确认旧进程真的退出了 —— 旧进程还占着端口时，新起的一个会静默失败、
你看到的仍是旧页面（用 `netstat -ano | findstr :8501` 找到 PID 再 `taskkill /F /PID <pid>`）。
